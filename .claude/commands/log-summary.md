Generate an AI-synthesized executive summary of daily work logs for a given time period.

**Language**: Read `LANGUAGE` from `.env` (default: `en`). Respond and generate all output in this language.

## Arguments

`$ARGUMENTS` specifies the time period. Accepted values:
- `week` — current week
- `last-week` — previous week
- `month` — current month
- `last-month` — previous month
- `YYYY-WNN` — specific ISO week (e.g. `2026-W12`)
- `YYYY-MM` — specific month (e.g. `2026-01`)
- (empty) — defaults to `last-week`

## Steps

1. Read the member identity from `.env` (the `MEMBER` variable). If not set, ask the user.

2. Determine the period from `$ARGUMENTS`. If empty, default to `last-week`.

3. Extract structured log data:
   ```bash
   ./hey log extract --member $MEMBER --period $PERIOD
   ```
   This returns JSON with mechanical extraction of daily logs: task references, timestamped log entries, condensed external signals, and reflection highlights.

4. Read the JSON output carefully. Then **synthesize** an executive summary. Do NOT just reformat the raw data. Instead, produce genuine insight by:

   **a) Executive Summary** (3-5 sentences)
   - What was the primary focus and outcome of this period?
   - Was there a dominant theme or was work fragmented across many fronts?

   **b) Task Progress Narrative**
   - For each task that appeared during the period, write a 1-2 sentence narrative: where it started, what happened, where it ended.
   - Flag tasks that were carried across multiple days without resolution.
   - Identify tasks that were planned but got zero attention.

   **c) Key Patterns & Insights**
   - What recurring patterns do you see? (e.g., context-switching, deep-focus days, debugging marathons)
   - What consumed more time than expected?
   - What shipped faster than expected?

   **d) Carried Blockers**
   - Items that appeared as open threads or blockers across multiple days.
   - Distinguish between: waiting on others, technical blockers, scope creep.

   **e) Actionable Recommendations**
   - Based on the patterns, what should the member consider changing?
   - What tasks are at risk of becoming perpetual carries?
   - Any process improvements suggested by the data?

5. Write the summary to the appropriate location (use `.ai.md` extension to avoid overwriting mechanical summaries):
   - For weekly periods: `workspace/$MEMBER/logs/summaries/weekly/$PERIOD.ai.md`
   - For monthly periods: `workspace/$MEMBER/logs/summaries/monthly/$PERIOD.ai.md`
   - The `.ai.md` extension distinguishes AI-synthesized summaries from mechanical ones generated by `hey log compact`.

6. Report to the user:
   - Show the executive summary inline
   - Confirm the file was written
   - Suggest running for other periods if useful

## Output Format

The written summary file should follow this structure:

```markdown
# [Weekly/Monthly] Summary: $PERIOD

> AI-synthesized from $N daily logs.

## Executive Summary
[3-5 sentence overview]

## Task Progress
| Task | Status Arc | Notes |
|------|-----------|-------|
| task_xxx | started → shipped | ... |
| task_yyy | carried W11→W12→W13 | at risk |

## Key Patterns & Insights
- [pattern 1]
- [pattern 2]

## Carried Blockers
- [blocker]: [waiting on X since YYYY-MM-DD]

## Recommendations
- [actionable item 1]
- [actionable item 2]
```

## Principles

- **Synthesize, don't summarize.** The mechanical extraction already exists via `hey log compact`. This command adds the human-like analysis layer.
- **Be specific.** Reference actual task IDs, dates, and concrete observations — not generic advice.
- **Flag risks early.** If a task has been carried across 3+ periods, call it out explicitly.
- **Respect the raw data.** Never fabricate details. If the logs are sparse, say so — don't fill gaps with assumptions.
